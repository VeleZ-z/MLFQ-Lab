## **1\. Objetivo**

Implementar un simulador de scheduler con política Multi-Level Feedback Queue (MLFQ) que incluya: Prioridades entre colas, Diferentes quantums por nivel, Democión por uso completo de quantum, Priority boost periódico, Cálculo de métricas: Waiting time, Turnaround time, Response time y exportar resultados en un archivo .csv.

**2\. Descripción Funcional**

1. Especificación del Scheduler  
   * Estructura de colas  
     1. Q0: prioridad alta, quantum \= 2 ciclos  
     2. Q1: prioridad media, quantum \= 4 ciclos  
     3. Q2: prioridad baja, quantum \= 8 ciclos  
   * Siempre se ejecuta la cola de mayor prioridad no vacía.  
   * Dentro de cada cola se usa Round Robin.  
2. Selección: ejecutar siempre el proceso en la cola de mayor prioridad disponible.  
   * Democión: si un proceso consume todo su quantum, baja un nivel.  
   * No democión: si termina antes de agotar el quantum, no baja.  
   * Priority boost: cada S ciclos (por ejemplo, cada 20 ciclos), todos los procesos vuelven a la cola de mayor prioridad.  
   * La simulación debe ser por ciclos de reloj (tiempo discreto).  
3. Cada proceso debe tener como mínimo:   
   * PID  
   * arrival\_time  
   * burst\_time  
   * remaining\_time  
   * start\_time  
   * finish\_time  
   * first\_response\_time  
   * current\_queue  
4. Métricas obligatorias  
   * Para cada proceso calcular:  
     1. **Response time**: first\_response\_time − arrival\_time  
     2. **Turnaround time**: finish\_time − arrival\_time  
     3. **Waiting time**: turnaround\_time − burst\_time  
5. Salida requerida  
   * Generar un archivo results.csv con el siguiente formato:

   

| PID | Arrival | Burst | Start | Finish | Response | Turnaround | Waiting |
| :---- | :---- | :---- | :---- | :---- | :---- | :---- | :---- |
| P1 | 0 | 10 | 0 |  |  |  |  |
| P2 | 2 | 6 | 4 |  |  |  |  |
| P3 | 4 | 4 | 6 |  |  |  |  |

   

6. Escenario de prueba sugerido  
   * Procesos:  
     1. P1: arrival=0, burst=8  
     2. P2: arrival=1, burst=4  
     3. P3: arrival=2, burst=9  
     4. P4: arrival=3, burst=5  
   * Priority boost cada 20 ciclos.  
7. Análisis:  
   * ¿Qué ocurre si el boost es muy frecuente?  
   * ¿Qué ocurre si no existe boost?  
   * ¿Cómo afecta un quantum pequeño en la cola de mayor prioridad?  
   * ¿Puede haber starvation?  
8. Evaluación de Calidad de Software (Buenas Prácticas, Principios y Patrones de Diseño)  
   * Además de la correctitud funcional del simulador, se evaluará la calidad del diseño del código. Esto busca que el estudiante no solo resuelva el problema, sino que produzca un sistema mantenible, extensible y fácil de razonar.  
     1. Buenas prácticas de programación (15%).  
     2. Nomenclatura clara: nombres de variables, funciones y clases que reflejan su propósito (evitar x, temp, datos2).  
     3. Funciones pequeñas y con una sola responsabilidad: evitar funciones de 100+ líneas que mezclan lectura de datos, lógica del scheduler y exportación de resultados.  
     4. Manejo de errores: validación de entradas (ej. burst\_time negativo, archivo de procesos mal formado) con mensajes claros, no fallos silenciosos.  
     5. Evitar código duplicado (DRY): por ejemplo, la lógica de mover un proceso entre colas no debería repetirse en cada nivel.  
     6. Comentarios útiles, no obvios: documentar el por qué de decisiones no triviales (ej. por qué se eligió cierta estructura para las colas), no explicar línea por línea lo que ya es evidente.  
     7. Pruebas mínimas: al menos un conjunto de pruebas unitarias que validen el cálculo de métricas y la lógica de democión/boost.  
   * Principios de diseño: Se evaluará evidencia de aplicación (no necesariamente nombrarlos explícitamente, pero sí que el diseño los refleje).  
     1. SRP (Single Responsibility Principle): separar claramente el modelo del proceso, la lógica del scheduler, el manejo de colas y la exportación de resultados en módulos/clases distintas.  
     2. OCP (Open/Closed Principle): el sistema debería permitir agregar una nueva política de cola (ej. una cola adicional o una regla de democión distinta) sin modificar el núcleo del scheduler.  
     3. DIP (Dependency Inversion): por ejemplo, que el scheduler dependa de una abstracción de "cola" y no de una implementación concreta amarrada directamente.  
     4. Encapsulamiento: el estado interno de un proceso o de una cola no debe ser modificado libremente desde cualquier parte del código.  
   * 3.3 Patrones de diseño (10% \+ puntos adicionales por justificación)  
     1. No es obligatorio usar patrones de diseño formales, pero se dará puntaje adicional si el estudiante identifica y aplica (con justificación explícita en el informe) patrones pertinentes, por ejemplo:	  
        1. Strategy: para encapsular la política de scheduling (permite intercambiar MLFQ por FCFS/RR sin tocar el motor de simulación).  
        2. State: para representar los estados de un proceso (NEW, READY, RUNNING, WAITING, TERMINATED).  
        3. Factory: para la creación de procesos a partir de distintas fuentes (archivo CSV, generación aleatoria, etc.).  
        4. Observer: si se decide registrar eventos de simulación (ej. cada vez que un proceso cambia de cola) para logging o métricas en tiempo real.  
   * Nota para el estudiante: usar un patrón de diseño sin necesidad real (over-engineering) resta puntos tanto como no usarlo cuando aporta valor. Se evalúa la pertinencia, no la cantidad.  
9. 3.4 \[Opcional con puntos adicionales\] Arquitectura limpia (hasta \+10%)  
   * Los estudiantes que estructuren su proyecto siguiendo principios de Clean Architecture (o Hexagonal/Ports & Adapters) obtendrán puntaje adicional. Se espera evidencia de:  
     1. Separación en capas: dominio (entidades Process, Queue, reglas del scheduler) independiente de infraestructura (lectura de archivos, escritura de CSV, I/O).  
     2. Independencia de frameworks/librerías externas en el núcleo de la lógica de negocio.  
     3. Regla de dependencia: las capas externas dependen de las internas, nunca al revés (ej. el dominio no debe importar librerías de manejo de CSV).  
     4. Un diagrama simple (puede ser en el README) que muestre las capas y sus dependencias.  
10. Entregable adicional: Se debe incluir un breve documento (DESIGN.md o sección en el README) donde el estudiante:  
    * Explique las decisiones de diseño tomadas.  
    * Justifique qué patrones/principios aplicó y por qué.  
    * Si aplicó arquitectura limpia, incluya el diagrama de capas.
